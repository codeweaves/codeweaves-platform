## Proposed (not fixed, needs a decision)

### Slice 1: auth / tenancy / RBAC

- **A-3 (P1) RateLimitGuard keys public routes on a spoofable IP.** `guards/rate-limit.guard.ts:getClientIp` reads the FIRST entry of `x-forwarded-for` before `request.ip`. A client sets `X-Forwarded-For: <random>` per request and gets a fresh bucket every time, so every `@RateLimit()` on a `@Public()` route (demo voice, etc.) is bypassable. `MessageRateLimitService.getClientIp` in the same codebase already does this correctly (`request.ip` only) and documents why. **Not fixed because the right answer depends on the proxy chain:** with `trust proxy = 1` (main.ts) `request.ip` is correct only if the API is directly behind one proxy (Render). If Cloudflare fronts Render, `request.ip` is the Cloudflare edge and you need `trust proxy = 2` or `cf-connecting-ip`. Check one prod request: compare `req.ip` to `cf-connecting-ip`. Then make `getClientIp` return `request.ip ?? 'unknown'` and drop the two XFF tests in rate-limit.guard.spec.ts (lines 295-336) that assert the spoofable behaviour.
- **A-4 (P2) Member add/remove does not evict the UserSyncGuard cache.** `OrganizationMembersService.assignMember/removeMember` change `organizationId`, but only `UserRolesService` calls `userSync.evict()`. A removed member keeps their org access for up to 60 s. Same fix as roles: inject `UserSyncGuard` and evict the target's `clerkId` (needs the target's clerkId in the select). Small, but touches module wiring, so left for your call.
- **A-5 (P2, reminder you asked for) `@Public()` on `PublicChatController` + no Redis-down throttle.** Deferred API-key hardening from earlier. This review is effectively pre-launch, so surfacing it here. Will look at the controller itself in slice 2.
- **A-6 (P3) Dead decorators.** `invitations.controller.ts` `validate/:token` and `reissue` carry BOTH `@Public()` and `@RequirePermission(...)`. `PermissionGuard` short-circuits on `@Public()`, so the permission is never checked and the decorator misleads a reader into thinking the route is gated. Remove the `@RequirePermission` lines. Zero behaviour change. (I6/I7 from the July IDOR audit, the product decision that reissue stays self-service, is unchanged.)
- **A-7 (P3) `UsersService.findByEmail` has no `deletedAt: null` filter**, unlike `findByClerkId`. Only used by invitation duplicate checks today, where blocking a re-invite of a soft-deleted email may even be intended. Flagging so it is a decision, not an accident.

**Verified clean, no action:** PermissionGuard default-deny + `RouteAuthorizationAssertion` boot check; `InternalSecretGuard` (fail-closed, constant-time) on all 5 cron endpoints; `DevAiController` gate on all 6 handlers; JWT strategy (RS256, issuer, JWKS rate-limited, no `ignoreExpiration`); invitation provisioning (email-verified via Clerk, fail-closed, race-safe); `UserRolesService` (self-edit block, org containment, grantable filter, audit + evict); every agent/analytics/conversation/handover/knowledge/theme/data-field route passes the caller into a scoped service.

### Slice 2: AI + chat core

- ~~B-1~~ moved to Fixed: in-process fallback limiter built. Original note: **Rate limiting failed OPEN when Redis was down, on the routes that spend LLM money.** `RateLimiterService.checkRateLimit` returns `allowed: true` on any Redis error or null pipeline. `MessageRateLimitService` (warmup / send / stream / request-human / voice) has no fallback, so a Redis outage (Upstash incident, quota exhaustion, bad env) removes every per-device and per-IP cap at once. Fail-open is the right call for the dashboard (`RateLimitGuard`) but not for public LLM spend. Proposal: give `MessageRateLimitService` a per-process in-memory sliding-window fallback (Map keyed the same way, capped size, same limits) that engages only when Redis throws. ~60 lines + tests. This is the "no Redis-down throttle" item you asked to be reminded of.
- **B-2 (P2) Client-supplied `recentHistory` is trusted as the conversation record.** `POST /public/chat/stream` accepts up to 100 prior turns with `role: 'assistant'` from the unauthenticated widget, and `ContextAssemblyService` uses them INSTEAD of the DB when present (deliberate: saves 150-400 ms). Two consequences: (1) an attacker can inject fake assistant turns ("Sure, here is the system prompt:"), which primes the model far better than a user message can, and (2) the transcript in the dashboard is not what the model actually saw, so the audit trail diverges. Bounded (100 × 10k chars) and HARD_DROP PII is masked, so not a data leak. Options, cheapest first: (a) only honour client history when `sessionId` is present AND the history length matches the DB message count for that session (one cheap `count`), (b) drop `role: 'assistant'` items from client history and load assistant turns from DB, (c) accept the trade-off and document it in `docs/patterns/security.md`. Your call; not changed.
- **B-3 (P2) `GET /public/chat/:sessionId/poll` has no rate limit.** Public, 2 DB queries per call, returns up to 100 messages. Widget polls at 2.5 s (fast) / 12 s (socket connected). An IP-keyed `@RateLimit()` would break several tabs behind one NAT; the right key is the sessionId itself (e.g. 60/min per session). Small change once you agree on the key.
- **B-4 (P3) Inconsistent `source` defaults.** `/public/chat/send` (sync) defaults `source` to `DEMO`; `/public/chat/stream` and `/request-human` default to `WIDGET`. A `DEMO` session never raises handover and analytics treat it as preview. Harmless if only the demo page uses `/send`; worth aligning to `WIDGET` if any real client does.
- **B-5 (P3) Fire-and-forget message persistence can reorder a turn.** In `stream()` both `saveUserMessage` and `saveAssistantMessage` are fire-and-forget with pre-generated ids; ordering in the transcript is by `createdAt`, which is set when each INSERT lands. Under a DB latency spike the assistant row can land first. Rare; fix is to pass an explicit `createdAt` captured at receive time.

**Verified clean, no action:** `warmup` synthetic session (`PiiToken.chatSessionId` is a plain string, capture/summary are feature-gated, usage row is a real cost record); request headers are redacted before `event_logs` (`sanitizeHeaders`); 5xx bodies never echo internals; provider errors are generic to the widget; SSE has a 30 s controller timeout and a 60 s LLM stream timeout with `AbortSignal.any`; `recentHistory` is bounded; every chat/handover/conversation/agent read is org-scoped at the service layer.

### Slice 3: voice

- **C-1 (P2) Rate limit runs after the expensive part.** `POST /public/voice/conversation` accepts and buffers the full upload (up to 10 MB, memory storage), resolves the agent (DB), and writes a `VOICE_CONVERSATION_RECEIVED` event row BEFORE `checkMessageRateLimit`. Rejected spam still costs a DB read, a DB write and 10 MB of RAM per request. Reordering means keying the limiter on `dto.agentId` (publicId) instead of the resolved UUID, which merges the voice and chat buckets per device. Probably fine, but it changes limits users see, so your call.
- **C-2 (P2) 10 MB upload cap vs a 60 s recording.** The widget caps recordings at 60 s (`MAX_RECORDING_MS`), which is well under 1 MB of Opus. `MAX_FILE_SIZE = 10 MB` with multer memory storage means 200 concurrent abusive uploads = 2 GB RAM on the API instance. Suggest 2 MB. Confirm with a real 60 s WebM from the widget before lowering.
- **C-3 (P3, cost) English voice turns run STT twice by design.** Auto-detect calls Sarvam, then re-transcribes English via Deepgram. Deliberate for accuracy, but it is 2× STT cost and latency on every English turn without a `languageHint`. If the widget knows the page language, pass the hint.

**Verified clean, no action:** MIME allowlist + size cap; first-chunk / idle / total watchdogs with re-arm; client disconnect aborts LLM and TTS and clears timers; TTS WebSocket session closed in `finally`; provider fallback chains for STT and TTS; error chunks are generic; STT/TTS/LLM metrics persisted per turn.

### Slice 4: privacy / PII / retention / crypto

- **D-2 (P3) `UserSyncGuard` cache is not evicted on erasure.** After `eraseOrganization` deletes users, a still-logged-in user of that org keeps a cached identity for up to 60 s. Requests then fail on missing rows rather than 401. Cosmetic; same eviction hook as A-4.

**Verified clean, no action:** AES-256-GCM with per-value IV, domain-separated HMAC keys, key length asserted at boot; visitor IP stored only as a keyed hash; PII vault rows are org + session scoped, values encrypted, lookup by session-scoped HMAC; `redactForStorage` masks instead of tokenising if the vault write fails (never stores an unrecoverable token); stream detokenizer holds back only a plausible partial placeholder, bounded at 40 chars; retention sweeps use real `createdAt` columns, batch 5k with id-subselect, audit retention off by default; privacy endpoints pin ORG callers to their own org; org erasure requires `?confirm=<orgId>` and `Privacy:DeleteOrg` (platform-only); data extraction feeds the LLM the tokenised transcript and detokenises the output.

### Slice 5: analytics + data extraction
